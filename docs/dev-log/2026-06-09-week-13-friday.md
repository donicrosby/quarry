## Cross-vendor disagreement: how it works

`CandidateFinding.hunter_provider` is a plain `str | None` set by the hunt stage to
whatever provider string the LiteLLM adapter reports (e.g. `"litellm"`, `"anthropic"`).

The validate role's panel config carries a `Provider` enum value (e.g. `Provider.MOCK`).
The activity compares the two after downcasing:

```python
cross_vendor = (
    hunter_provider.lower() != validate_provider.lower()
    and bool(hunter_provider)
    and bool(validate_provider)
)
```

In the Week 13 demo panel:

```python
_CROSS_VENDOR_PANEL["validate"] = RoleConfig(provider=Provider.MOCK, model="mock-v1")
# findings carry hunter_provider="litellm"
# "litellm" != "mock" → cross_vendor_disagreement = True ✓
```

All three hunt findings in the demo produce `cross_vendor_disagreement = True`.

## Coverage-floor invariant

`enforce_coverage_floor` in `src/quarry_models/coverage.py` is a pure Python function —
not a prompt, not a model instruction. It counts existing tasks per focused `vuln_class`
and pads to `min_per_class=2` with synthetic `source="gapfill"` tasks.

Demo result with `FOCUSED = [COMMAND_INJECTION, XSS]` and 3 existing tasks
(2 CI, 1 XSS):

```
COMMAND_INJECTION: 2 existing → floor already satisfied
XSS: 1 existing → floor adds 1 → total 2 ✓
```

```

cf-2  ✗ dropped
cf-3  ✓ kept
```

## ADR decisions

- **ADR-021** (`docs/decisions/adr-021-validate-independence.md`): validator independence
  boundary — `ValidatorClaim` carries only `file, line_start, line_end, vuln_class,
  description, affected_code_snippet`; hunter reasoning, provider, model name, and tool
  trace are explicitly forbidden. Coverage floor is a Python invariant, not a prompt.
