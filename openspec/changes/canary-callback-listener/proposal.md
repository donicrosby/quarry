# Change: canary-callback-listener

## Why

SSRF and XXE are proven not by inspecting a target's HTTP response but by observing an out-of-band callback — the target fetches a canary URL (SSRF) or parses an XML external entity pointing at it (XXE). Without an OOB listener, these vulnerability classes cannot be proved against a live target, and the prove stage falls back to `inconclusive` for every SSRF/XXE candidate.

The D1 egress-policy change (`egress-policy-destination-sets`) built the containment primitive the canary needs — a per-policy `--internal` Docker network the sandbox shares with trusted infrastructure — plus the `CANARY_LISTENER` destination-set name, the `needs_canary` flag on `build_prove_sandbox_policy`, and the `canary_destinations` parameter on `build_egress_policy`. The listener itself and its proof integration were deferred to this change (the `needs_canary` flag has no caller and `canary_destinations` is always empty).

## What Changes

- **Canary listener lifecycle**: A new canary listener runs as infrastructure co-located with the sandbox. Tier 1: a background thread on `127.0.0.1` (ephemeral port) in the worker process. Tier 2: a sidecar container on a host-reachable address (host network mode or published port) so the external target can reach it. The listener is started and stopped inside the `sandbox-exec` activity, not as separate Temporal activities; the activity input gains `canary_token: str | None`. The activity sets `QUARRY_CANARY_URL` in the sandbox environment before command execution.

- **Proof prompt injection**: The workflow generates a deterministic canary token (SHA-256 hash of finding ID + attempt index, Temporal replay-safe). The prompt instructs the agent to use `$QUARRY_CANARY_URL` as the callback target; the literal URL is set by the activity, not constructed in the workflow.

- **Canary evidence collection**: After the sandbox executes, the activity collects the listener's request log and returns it as `CanaryCallback` entries on the `SandboxExecCapture`. Only safe fields are captured: `method`, `path`, `source_ip`, `timestamp` — no request headers or body.

- **Verdict integration**: Canary evaluation is integrated directly into `prove_outcome_from_captures`, not the verdict-evaluator registry. `ssrf_evaluator` (HTTP response differential, min_probes=2) remains unchanged. For SSRF/XXE, a canary callback from an authorized target IP with a token-bearing path yields `corroborated` and outranks HTTP inspection. Source IP filtering blocks self-forged callbacks: callbacks from `127.0.0.0/8` (Tier 1 sandbox loopback) or the sandbox container's IP (Tier 2) are logged but do NOT corroborate.

- **Destination-set correction**: The canary listener is infrastructure on the sandbox's network, not a destination set. This change adds an ADDED requirement ("Destination-set configuration with canary sidecar activation") superseding D1's "Destination-set-aware proof configuration" requirement, replacing `canary-listener` as a destination set with the sidecar model. `needs_canary=True` signals the sandbox-exec activity to start the sidecar; `canary_token` on the activity input is the real activation signal.

## Impact

- **Specs**: `proof-and-sandbox-execution` (MODIFIED: Destination-set-aware proof configuration; ADDED: canary callback proof, canary URL injection, canary evidence evaluation), `sandbox-backends` (ADDED: canary listener lifecycle, bind safety and data capture).
- **Code**: `src/quarry_activities/sandbox_exec.py` (canary sidecar lifecycle with tier-specific topologies), `src/quarry_activities/inputs.py` (new `canary_token` field on `SandboxExecActivityInput`), `src/quarry/schemas.py` (new `CanaryCallback` model on `SandboxExecCapture`, safe-fields-only), `src/quarry_workflows/prove_stage.py` (`prove_outcome_from_captures` extension with canary evaluation), `src/quarry_workflows/run_scan.py` (deterministic token generation, `needs_canary` wiring, prompt injection), `src/quarry_activities/sandbox.py` (Tier 2 host-reachable canary sidecar container), `prompts/prove/prove.1.0.0.j2` (canary URL instruction via `QUARRY_CANARY_URL` env var).
- **Threat model**: The canary listener SHALL bind only to addresses appropriate for its tier: `127.0.0.1` only for Tier 1 (fail-closed on non-loopback), host-reachable for Tier 2. The listener SHALL log only safe fields (no headers/body) and respond with a fixed JSON body. Source IP filtering SHALL reject callbacks from the sandbox's own address space. The sandbox container in Tier 2 SHALL NOT have a route to the canary (the canary is not in any destination set; Tier 2 sandbox egress is restricted to target IPs only). This is the containment invariant: the sandbox can reach the target, the target can reach the canary, but the sandbox cannot reach the canary directly.
- **Non-goals**: No per-request path filtering beyond token matching (the token in the path is the authorization ceiling); no egress logging/tracing product; no change to the D1 Tier-2 network enforcement (must not widen `quarry-egress-*` — the canary is a sidecar on a host-reachable address, not on the internal network, preserving the D1 containment invariant); no browser-based OOB.

## Ambiguities resolved

1. **Topology per tier**: Tier 1 runs the canary listener on `127.0.0.1` (ephemeral port) in the worker process. The sandbox subprocess shares the host network and can reach external targets. Source IP filtering distinguishes target callbacks (non-loopback) from sandbox self-calls (127.0.0.1). Tier 2 runs the canary listener as a sidecar on a host-reachable address (host network mode or published port). The sandbox container's egress policy restricts it to target IPs only — it cannot reach the canary. The external target can reach the canary at the host address. This topology satisfies the containment invariant: sandbox -> target (authorized), target -> canary (callback), sandbox -/-> canary (blocked by egress policy).
2. **Activity shape**: The canary lifecycle is internal to `sandbox-exec`, not separate activities. The activity input gains `canary_token: str | None`. The activity starts the listener, sets `QUARRY_CANARY_URL` in the sandbox environment, runs the sandbox, stops the listener, and returns collected callbacks. The URL is constructed inside the activity (where the port is known), not in the workflow.
3. **Proof consumption**: The workflow generates a deterministic token and passes it to the activity and the prompt template. The prompt instructs the agent to reference `$QUARRY_CANARY_URL`. Canary evaluation is direct integration in `prove_outcome_from_captures`, not a verdict-evaluator registry entry. `ssrf_evaluator` is untouched. Source IP filtering validates that callbacks originate from the target, not the sandbox.
4. **Egress wiring / destination-set correction**: The canary listener is infrastructure, not a destination set. `needs_canary=True` on `build_prove_sandbox_policy` adds `CANARY_LISTENER` to the `wanted` set (documented signal; no mechanical effect when `canary_destinations` is empty). The real activation signal is `canary_token` on the activity input. D1's "SHALL receive the `canary-listener` set" requirement is superseded by an ADDED requirement in this change. When this change and D1 are both archived, the superseding requirement takes priority.
