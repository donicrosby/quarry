# Change: canary-callback-listener

## Why

SSRF and XXE are proved not by inspecting a target's HTTP response but by observing an out-of-band callback — the target fetches a canary URL (SSRF) or parses an XML external entity pointing at it (XXE). Without an OOB listener, these vulnerability classes cannot be proved against a live target, and the prove stage falls back to `inconclusive` for every SSRF/XXE candidate.

The D1 egress-policy change (`egress-policy-destination-sets`) built the containment primitive the canary needs — a per-policy `--internal` Docker network the sandbox shares with trusted infrastructure — plus the `CANARY_LISTENER` destination-set name, the `needs_canary` flag on `build_prove_sandbox_policy`, and the `canary_destinations` parameter on `build_egress_policy`. The listener itself and its proof integration were deferred to this change (the `needs_canary` flag has no caller and `canary_destinations` is always empty).

## What Changes

- **Canary listener lifecycle, tier-split**: A new canary listener runs as infrastructure co-located with the sandbox, with different roles per tier. Tier 1 (`LocalSubprocessSandbox`): a background thread on `127.0.0.1` (ephemeral port) in the worker process, logging-only. Tier 2 (`ContainerSandbox`): a sidecar container on a host-reachable address attached to the target's network, source-IP-filtered corroboration. The listener is started and stopped inside the `sandbox-exec` activity, not as separate Temporal activities; the activity input gains `canary_token: str | None`. The activity sets `QUARRY_CANARY_URL` in the sandbox environment before command execution.

- **Proof prompt injection**: The workflow generates a deterministic canary token (SHA-256 hash of finding ID + attempt index, Temporal replay-safe). The prompt instructs the agent to use `$QUARRY_CANARY_URL` as the callback target; the literal URL is set by the activity, not constructed in the workflow.

- **Canary evidence collection**: After the sandbox executes, the activity collects the listener's request log and returns it as `CanaryCallback` entries on the `SandboxExecCapture`. Only safe fields are captured: `method`, `path` (length-capped), `source_ip`, `timestamp` — no request headers or body.

- **Verdict integration (Tier-2-only corroboration)**: Canary evaluation is integrated directly into `prove_outcome_from_captures`, not the verdict-evaluator registry. `ssrf_evaluator` (HTTP response differential, min_probes=2) remains unchanged. For SSRF/XXE, a canary callback from an authorized target IP with a token-bearing path yields `corroborated` and outranks HTTP inspection — but **only in Tier 2**. Tier 1 callbacks are logged but never corroborate: on a loopback-bound listener every natural callback presents source `127.0.0.1`, so source IP is not a trustworthy discriminator there.

- **Resolved-IP transport**: The `sandbox-exec` activity returns the resolved target IPs on `SandboxExecCapture.resolved_target_ips` (from the resolved egress policy's `target-host` set), so the pure workflow-side evaluator can compare callback source IPs against the pinned target IPs without doing DNS. Corroboration requires a non-empty `resolved_target_ips`, which structurally makes it Tier-2-only (Tier 1 runs with an empty egress policy).

- **Destination-set correction**: The canary listener is infrastructure on the target's network, not a destination set. This change adds an ADDED requirement ("Destination-set configuration with canary sidecar activation") superseding D1's `canary-listener` destination-set model and D1's un-archived sandbox-backends scenario "Multi-destination policy reaches canary and target". `canary_token` on the activity input is the sole activation signal; `needs_canary` on `build_prove_sandbox_policy` is an inert workflow-side wanted-set marker.

## Impact

- **Specs**: `proof-and-sandbox-execution` (ADDED: destination-set configuration with canary sidecar activation [superseding D1], canary callback proof, canary URL injection, canary evidence evaluation), `sandbox-backends` (ADDED: canary listener lifecycle, bind safety and data capture).
- **Code**: `src/quarry_activities/sandbox_exec.py` (canary sidecar lifecycle with tier-specific topologies; populate `resolved_target_ips`), `src/quarry_activities/inputs.py` (new `canary_token` field on `SandboxExecActivityInput`), `src/quarry/schemas.py` (new `CanaryCallback` model and `resolved_target_ips` field on `SandboxExecCapture`), `src/quarry_workflows/prove_stage.py` (`prove_outcome_from_captures` extension with Tier-2-only canary evaluation), `src/quarry_workflows/run_scan.py` (deterministic token generation, `needs_canary` wiring, prompt injection, Tier-1 empty-policy dispatch), `src/quarry_activities/sandbox.py` (Tier 2 host-reachable canary sidecar container; `--cap-drop NET_RAW` when a canary is active), `prompts/prove/prove.1.0.0.j2` (canary URL instruction via `QUARRY_CANARY_URL` env var).
- **Threat model**: Tier 1 SHALL bind `127.0.0.1` only (fail-closed on non-loopback) and SHALL log but never corroborate. Tier 2 SHALL run the canary as a sidecar attached to the target's reachable network; containment is **source-IP-based, not route-based**: the evaluator SHALL corroborate only callbacks whose `source_ip` matches a resolved target IP, and the sandbox container SHALL drop `NET_RAW` (and `NET_ADMIN`) while a canary is active so it cannot spoof the target's source IP. The canary is NOT in any destination set (Tier 2 sandbox egress is restricted to `target-host` only), but the sandbox SHALL NOT be assumed unable to route to the attached canary — the source-IP filter plus the `NET_RAW` drop is the containment invariant.
- **Non-goals**: No per-request path filtering beyond token matching (the token in the path is the authorization ceiling); no egress logging/tracing product; no change to the D1 Tier-2 network enforcement (the canary is a sidecar on a host-reachable address, not on the sandbox's `--internal` network); no browser-based OOB.

## Ambiguities resolved

1. **Topology per tier**: Tier 1 runs the canary listener on `127.0.0.1` (ephemeral port) in the worker process, for CLI-only prove with an empty egress policy; callbacks are logged but never corroborated because a loopback listener presents source `127.0.0.1` for every natural callback. Tier 2 runs the canary as a sidecar attached to the target's reachable network (host-reachable address), and the target reaches it at a pinned host URL. Corroboration is Tier-2-only and source-IP-filtered.
2. **Activity shape**: The canary lifecycle is internal to `sandbox-exec`, not separate activities. The activity input gains `canary_token: str | None`. The activity starts the listener, sets `QUARRY_CANARY_URL` in the sandbox environment, runs the sandbox, stops the listener, and returns collected callbacks plus `resolved_target_ips`. The URL is constructed inside the activity (where the port is known), not in the workflow.
3. **Proof consumption**: The workflow generates a deterministic token and passes it to the activity and the prompt template. The prompt instructs the agent to reference `$QUARRY_CANARY_URL`. Canary evaluation is direct integration in `prove_outcome_from_captures`, not a verdict-evaluator registry entry. `ssrf_evaluator` is untouched. The evaluator compares `CanaryCallback.source_ip` against `SandboxExecCapture.resolved_target_ips` (returned by the activity — no DNS in workflow code).
4. **Tier-1 dispatch / egress policy**: `LocalSubprocessSandbox` rejects any non-empty egress policy (`sandbox.py` raises `EgressPolicyError`), so a Tier-1 prove SHALL be CLI-only and receive an empty policy (`needs_live_target=False`). Live-target egress is scoped to Tier 2 (`ContainerSandbox`). No dispatch combines a live target with the local backend.
5. **Egress wiring / destination-set correction**: The canary listener is infrastructure, not a destination set. `needs_canary=True` on `build_prove_sandbox_policy` adds `CANARY_LISTENER` to the `wanted` set (documented signal; no mechanical effect when `canary_destinations` is empty). The sole activation signal is `canary_token` on the activity input. D1's "SHALL receive the `canary-listener` set" requirement and its sandbox-backends scenario "Multi-destination policy reaches canary and target" are superseded by this change's ADDED requirement; when both changes are archived, this change's requirement takes priority and D1's `canary-listener` set and scenario are withdrawn.
6. **Tier-2 containment**: Containment is source-IP-based, not route-based. The attached canary is reachable by both target and (in some topologies) the sandbox; the invariant is that the evaluator SHALL corroborate only target-IP callbacks and the sandbox SHALL drop `NET_RAW` so it cannot forge the target's source IP. `--cap-drop NET_RAW` applies only while a canary is active; ping-based proofs without a canary keep their raw sockets.
